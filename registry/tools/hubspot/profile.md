## What it is (the vendor's words)

The company is HubSpot, Inc.; the terms page that names it was not fetched for this entry. The product, in the vendor's machine-facing [llms.txt](https://www.hubspot.com/llms.txt) read 2026-09-17, is a "customer platform that unifies customer data, gives teams a complete view of every customer", with Marketing, Sales, Service, Content, Data and Revenue Hubs and Agent Hub, and Breeze, which "surfaces customer intelligence, automates workflows, and powers AI agents embedded in every hub". **Withdrawn 2026-09-17:** three quotations stood here, among them "HubSpot's built-in AI platform", taken from `/products/marketing/ai` and on no live page (see Pricing).

For agents calling in, the vendor publishes the [HubSpot MCP server](https://developers.hubspot.com/ai-tools/mcp) (Remote): it "enables you to give any MCP-compatible AI tool or agent secure read and write access to your HubSpot CRM data". A local Developer MCP server serves the CLI, not this entry's surface; "Both require using the latest Developer Platform version."

The [integration guide](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server) is where the surface is actually specified. Every quotation from it below is taken from the Markdown representation at that path plus `.md`, read 2026-09-17. Connection: the client is configured "using your connector's OAuth credentials", and "PKCE is required for authenticating with HubSpot's MCP server." Read access covers "contacts, companies, deals, tickets, leads, users, appointments, courses, listings, projects, services, custom objects, and segments (lists)", with "Revenue objects (carts, invoices, orders, line items, products, quotes, subscriptions) are available in BETA", plus activities, content, conversations, marketing emails and account data. Write access covers "create and edit contacts, companies, deals, tickets, leads, line items, products, appointments, courses, listings, projects, services, and custom object records", activities, content, campaigns, email drafts and pipelines. "All actions respect your existing HubSpot user permissions. Users can only view and modify records they have access to in HubSpot."

Three sentences there matter more than the feature list. On scopes: "you don't explicitly define the connector's scopes. Instead, available scopes are automatically determined by two factors", namely "The tools available in the MCP server at the time of installation" and "The permissions that the user chooses to grant during installation", with the consequence stated, "As the MCP server's tools are updated, the available scopes may change. In the event of scope updates, users who have already installed the connector will need to re-install to grant any new scopes." **Correction, 2026-09-15:** an earlier version stopped at "may change" and concluded that an installed connector's powers are not fixed. The next sentence says the opposite, so the quotation above carries both. What is unusual is narrower: **the installer does not declare the scope set at all.** It is derived from the tools the server ships at install time and the permissions the user grants then, the opposite of Atlassian's model for Rovo, whose scope list is a document anyone can read before installing. On the engine: "Behind the scenes, the HubSpot MCP server is based on the CRM search API, which currently doesn't include vector search capabilities." And on a restriction that applies to agents only: "if your HubSpot account has Sensitive Data turned on, activity (e.g., calls, emails, meetings, notes, and tasks) and conversation data will be blocked from access through the MCP server. This restriction is specific to the MCP server and does not apply to the standard CRM APIs." The first case here of a vendor documenting an agent surface deliberately **narrower** than its own API for the same account.

The server's code is not published, so `source` is null. There are two `llms.txt`, of different kinds: `https://www.hubspot.com/llms.txt` is prose for a machine reader ("HubSpot is an AI-native customer platform"), `https://developers.hubspot.com/docs/llms.txt` a 40 KB link index advertised in the docs header as "Fetch the complete documentation index at: /docs/llms.txt". `llmsTxt` records the first, which sits on the homepage host.

**Correction, 2026-09-16: version 1 recorded a read-only server, and the correction to it then said the page had been rewritten under it. Both were wrong, the second one worse.**

Version 1 (2026-09-11) found a section headed "Read-only access" and recorded the server as read-only over the same page's "read and write" sentence. Version 2 (2026-09-15) said that heading and three other strings were gone from the redirect target. The reviewer could not reproduce it and was right: all four are live on [`/ai-tools/mcp`](https://developers.hubspot.com/ai-tools/mcp), extracted and published at [evidence/hubspot/2026-09-16](https://plumb.public-agents.ai/evidence/hubspot/2026-09-16/README.md). Before recording that a vendor sentence is gone: say where you looked, publish what you read.

The original error was a **reading** error. "Read-only access" is not a description of the server: it is one of two sub-headings splitting a list by object family, against "Read and write access" for CRM objects and engagements. The structured fields follow the integration guide, which documents the same split per object.

The landing page contradicts itself. Read 2026-09-16: "HubSpot MCP server supports OAuth 2.0. Later in 2025, we will align with MCP specification requirements for OAuth 2.1 support", then, next sentence, "MCP clients connecting to our server will need to implement OAuth 2.1 authentication, including: PKCE (Proof Key for Code Exchange) and Refresh token rotation (single-use refresh tokens)." A 2025 roadmap beside a present-tense requirement, read in September 2026. The wire narrows it, measured 2026-09-16: `mcp.hubspot.com/.well-known/oauth-authorization-server` answers 200 with `code_challenge_methods_supported: ["S256"]`, so PKCE is live; `token_endpoint_auth_methods_supported` is `["client_secret_post"]` alone with **no `registration_endpoint`**, so a client can be neither self-registered nor public; `client_credentials` is among the advertised grants, not exercised. No metadata document states a protocol version or whether refresh tokens are single-use, so the contradiction stands unresolved here.

## Can an agent use it without an account? (measured)

No. Re-measured 2026-09-15: an MCP `initialize` request to `https://mcp.hubspot.com/` with no credentials from a cloud IP answers 401 with an empty body and `www-authenticate: Bearer resource_metadata="https://mcp.hubspot.com/.well-known/oauth-protected-resource"`; that metadata answers `{"resource":"https://mcp.hubspot.com","authorization_servers":["https://mcp.hubspot.com"],"scopes_supported":[],"resource_documentation":"https://developers.hubspot.com/mcp"}`, byte for byte what it answered on 2026-09-11 at 23:45Z. A bare `GET` answers 401 too. Every documented path is a HubSpot account's credential through a connector created inside the account, so `noAccountNeeded` is false and `auth` is `oauth`; no headless alternative is named on the pages read. Two details: `scopes_supported` is empty, consistent with scopes decided at install time rather than declared, and `resource_documentation` still points at the URL that redirects, so a client following the machine-readable pointer lands on a 301.

## Jobs

Two claimed, both the vendor's claims for agents that run inside HubSpot, neither measured.

`sales.draft-outreach`, on the vendor's [use-case page](https://www.hubspot.com/products/artificial-intelligence/use-cases/send-personalized-sales-outreach), the claim's source: Breeze uses "CRM data and real-time signals to craft personalized outreach at the right time", and "Reps review the agent's research and drafted outreach, then approve before anything sends." The job's outcome is a first message drafted from what is known about the prospect and sent with light edits, and the vendor's words cover research, draft and approval, the whole outcome as the job states it. The [Prospecting Agent](https://www.hubspot.com/products/sales/ai-prospecting-agent) page says the same in fewer words: it "researches accounts, finds the right contacts, and drafts personalized outreach". Its edition is established as of 2026-09-17 and was not before: "Prospecting agent is available at the Starter, Professional, and Enterprise editions of HubSpot and runs on HubSpot Credits".

`cs.deflect-tier1`, re-sourced 2026-09-17 on the vendor's [customer agent page](https://www.hubspot.com/products/artificial-intelligence/ai-customer-service-agent), the claim's source, checked against both representations in the artifact. The vendor's own sentences for the outcome: "Customer agent resolves questions, takes action in your CRM, and hands off to your team with full context", and, in its FAQ, "HubSpot's customer agent is an AI-powered support agent that automatically handles customer inquiries, resolves tickets, and escalates complex issues to your team". The job's outcome is a routine customer request answered correctly and closed with no person handling it; the vendor claims the closing-without-a-person half in those words. The page names no request kinds, so the job's examples (password reset, order status) match no live vendor sentence and are not claimed here.

**What the 70% is, and what versions 1 and 2 said it was.** Under the heading "Real results from customer agent users." the page prints three figures, the first "70%" over "average resolution rate (top teams hit 90%)". Those are outcomes the vendor attributes to its customers: no method, no denominator, no date. The **billing** metric is stated separately on the same page: "Customer agent is priced per conversation resolved, at $0.50 per resolution. A resolution means support was provided by the agent, and the conversation was not handed to a human rep for 72 hours. A resolution can also occur if customer agent qualifies a lead." Versions 1 and 2 said the 70% **was** that billing metric. It is not, nothing on the page connects the two, and the error ran in the direction that makes a marketing statistic look like a contractual definition. This registry has measured neither. Worth keeping is the definition: a resolution is **no handoff within 72 hours**, or a qualified lead, and nothing in it tests whether the answer was right, the word the job puts first.

The page also carries named customer testimonials with their own figures: practitioners' reports, selected and published by the vendor, with no method and no denominator, not recorded as measurements here.

Whether the MCP surface reaches either agent is not established; the page read describes the server as read access to CRM data. The claims are for the products.

Not claimed: `sales.enrich-leads` (the vendor sells data enrichment, and version 1 quoted a sentence for it from a page it had not read, withdrawn 2026-09-17; the enrichment page is still unread here), `sales.update-crm-from-conversations`, `sales.score-leads` and `cs.draft-agent-replies`.
