This is an unclaimed listing: MCP Guard did not write it, and nothing here is verified by the vendor. It records what the vendor's own public pages say and what a keyless probe of its endpoint returned on 2026-11-19.

MCP Guard (mcp-guard.ai) is a hosted service that checks a single proposed AI-agent tool call before it runs and returns a verdict. Its [llms.txt](https://mcp-guard.ai/llms.txt) describes it as a service that "checks an AI agent's tool call before it runs and returns a verdict (allow / ask / block) plus calibrated scores for nine questions (safe, violation, severity, destructive, exfiltration, injected, approval_policy, blast_radius, args_grounded), from one forward pass of a small model." The same file names the model: "DeBERTa-v3-base (184M parameters) fine-tuned on ~31k labelled agent actions". The vendor adds a caution in its own words: "It reduces risk; it does not guarantee safety."

## The surface an agent reaches

MCP Guard is itself agent-accessible. It runs a first-party MCP server at `https://api.mcp-guard.ai/mcp` (Streamable HTTP), and the [MCP server page](https://mcp-guard.ai/docs/mcp) frames it as a tool the agent calls: "Give any MCP client the guard as a tool: it can check an action before running it, or check every call a script is about to make." That page lists three tools: `guard_check` (one credit), `guard_batch` (one credit per check, up to 64 per request), and `usage` (free). The core tool's job is stated plainly: "Judge a tool call BEFORE executing it. Returns verdict (allow / ask / block), p_unsafe, reasons, and calibrated scores for nine questions". The same facility is also a REST endpoint (`POST /v1/guard`, `POST /v1/guard/batch`, `GET /v1/usage`), per the llms.txt.

## Why it claims it.review-agent-tool-actions, and where the claim stops

The job asks that a high-risk agent tool action receive a policy decision before it can change systems, with allowed actions proceeding and others denied or sent for a human decision. That is exactly what `guard_check` returns: a per-call verdict of allow, ask, or block, before execution. The docs map the three verdicts onto the job's three outcomes: "Run the action on allow, ask the user on ask, never run it on block; if the check fails, treat the action as ask." So the claim rests on the vendor's documented pre-execution verdict.

Two limits keep the claim bounded, and both are the kind the job definition itself names.

First, MCP Guard decides; it does not enforce. It returns a verdict, and the calling agent or harness has to honor it ("never run it on block"). Nothing in the surface stops a caller that ignores a block. The job warns that "a review record alone is not proof that an action was blocked", and that applies here: coverage depends entirely on the integration passing every risky call through the guard and obeying the answer. Even for a call that is submitted, the model reads only a bounded slice of it: the [MCP server page](https://mcp-guard.ai/docs/mcp) says "The model reads about 384 tokens per check in total: when the fields are longer they are trimmed, keeping the newest turns and the start and end of long fields (recipient and target arguments are kept), and the response reports truncated: true". So the verdict is formed on that trimmed context, not necessarily on the full arguments of the call.

Second, the verdict is produced by a model sharpened by a small fixed rule set, not by an administrator-configured permission ruleset. MCP Guard scores a call with a fine-tuned classifier and derives a verdict from thresholds on those scores; on top of that the [Scores & verdicts guide](https://mcp-guard.ai/docs/scores) says "the server applies three deterministic policy rules that can raise a verdict to ask (never lower it)". The three it names are `irreversible` (a likely destructive call whose tool name is a delete, drop, purge, cancel or payment-type verb), `unnamed_recipient` (sending or sharing to a domain the user never named), and `outbound_exfiltration` (an outbound action with an elevated exfiltration score). So a caller receives a combined decision, and the response's `triggers` distinguish a rule that fired (`source: "policy"`, naming the rule and the field it looked at) from a score that crossed its threshold (`source: "model"`). These rules are the vendor's own, fixed, and keyed to tool names and recipient domains; they are not a policy an administrator writes, and they do not make the service an enforcement boundary. The scores are exposed precisely so a caller can set its own stricter thresholds on top. The judgment is therefore a vendor-set mix of a probabilistic model and a few deterministic heuristics, not a lookup against a permission set the operator declares, and it still decides rather than enforces. That is a different mechanism from the gateway and policy-engine products in the same space, and it is worth stating so a reader does not assume administrator-defined rule-based enforcement.

## The vendor's own accuracy claim, recorded as a claim

MCP Guard publishes an evaluation of itself, and it is the vendor's own measurement, not a third party's. The llms.txt reports "AUROC 0.855 on R-Judge (held-out test half, 304 trajectories) vs 0.824 for saroku-guard; the difference is not yet statistically significant". R-Judge is a public agent-safety benchmark; the comparison figure is attributed to another guard. This is the vendor asserting its own effectiveness on a named benchmark, with its own caveat that the margin is not yet significant. It is recorded here as a vendor claim. It does not fill any of the job's measures, which ask about operational coverage and error rates in deployment, not a benchmark AUROC.

## Access and ownership

Reaching the guard needs an API key from the dashboard, which needs an account, so `noAccountNeeded` is false. A keyless `POST initialize` to `https://api.mcp-guard.ai/mcp` on 2026-11-19 returned HTTP 401 with `WWW-Authenticate: Bearer realm="MCP Guard", error="invalid_token"` and a JSON-RPC body `-32001` with `code "missing_api_key"`, instructing the caller to send `Authorization: Bearer mcpg_live_...`; the docs say the `x-api-key` header works too. That is first-hand evidence that the endpoint exists and gates on a bearer key. No `/.well-known/public-agents.json` was served at the homepage (404 on 2026-11-19), so provenance is third-party and this entry is unverified, in those words, until the domain acknowledges it.

## Pricing

MCP Guard is freemium with a one-time free grant rather than a recurring free tier. The [pricing page](https://mcp-guard.ai/pricing) lists "$0.20 per 1,000 checks" and says "One check is one tool call judged on all nine questions." Every new workspace gets 1,000 free requests, which is enough to use the guard before any payment; that grant is one-time, not renewing. Beyond it, a buyer can purchase credit packs ($5, $25, $100) or subscribe to a monthly plan (Starter $19, Pro $99, Scale $399), and failed calls are never billed. Payment is by card. The [FAQ](https://mcp-guard.ai/faq), under whether a card is needed to start, says "After that you add a card to buy a pack or a plan", which names the instrument; the [terms](https://mcp-guard.ai/terms) add that "Payments are processed by Stripe under its own terms", which names only the processor. So `methods` is card and `humanBilling` is prepaid-credits. It is not machine-payable: there is no documented agent-settled payment path, only a human buying credits. Consumers in the EU, EEA and UK have a 14-day withdrawal right, and purchased credits are otherwise non-refundable.

## Hosting and data

The llms.txt states that "request payloads are not stored; request metadata kept 30 days", and that inference runs on GPUs in Switzerland with EU failover. This is relevant to anyone routing tool-call arguments, which can carry sensitive data, through a third party for a verdict. It is the vendor's statement, not verified here.

## Measures

All of the job's measures are empty. No third-party figure for the share of risky actions checked, the share of unauthorized actions executed, the false-positive rate, or the time to decide actions that need human approval was found. The vendor's AUROC and its self-reported inference latency (about 15 ms per check on an RTX 4090) are its own numbers and are recorded above as claims; note the job's latency measure asks how quickly actions needing human approval are resolved, which is not the model's per-check inference time.
