## Three agent surfaces, which the vendor keeps apart

[The Wix MCP](https://dev.wix.com/docs/overview/ai-the-wix-platform/the-wix-mcp): "lets you work with Wix from your AI agent. Once you connect it, your agent can search the Wix documentation, write code for the Wix platform, and make API calls on Wix sites." Among its capability groups: "Your agent can perform account-level actions, like creating and publishing a site, installing a business solution, or scaffolding a new headless project." On auth: "By default, your agent authenticates through your Wix account", with an API key and account ID as the alternative "For tools that run without an interactive login". The vendor's own note draws the line this entry keeps: "The Wix MCP connects your AI agent to Wix", and the Site MCP "goes the other direction, connecting visitors' AI agents to a single Wix site". The [product page](https://www.wix.com/studio/developers/mcp-server) answers "Do I need a Wix account? Yes, if you don’t have a Wix account you’ll be prompted to create one as you chat with your preferred LLM about your project."

[The Wix Site MCP](https://dev.wix.com/docs/develop-websites/articles/get-started/ai-agents/about-the-wix-site-mcp): "Anyone can connect their compatible AI agent to the MCP server of any Wix site." The endpoint is the site's own URL followed by `/_api/mcp`, and "You don't need to include authentication for site MCPs." The note on what such a client is: "An external client that connects to the site's MCP server acts as an anonymous site visitor." The vendor's [help-centre article](https://support.wix.com/en/article/ai-tools-connecting-wix-sites-to-ai-platforms) adds "The Wix MCP is active by default on every Wix site", "No, the MCP server is provided by Wix for free when you create a site", and "The MCP only uses public information that’s already available on the business’s site."

[The Wix WebMCP](https://dev.wix.com/docs/develop-websites-sdk/get-started/ai-agents/about-the-wix-web-mcp) "lets AI agents that run inside a visitor's browser work with a Wix site through structured tools instead of reading the page and clicking through it", built on a proposed web standard "incubated in the W3C Web Machine Learning Community Group"; it runs on top of the Site MCP and is opt-in per site via an app. Not measured: it needs a browser that exposes `document.modelContext`.

## Can an agent use it without an account? (measured)

**The Wix MCP: no.** At 06:12:26Z an `initialize` and a `tools/list` to `https://mcp.wix.com/mcp` with no credential each answered 401 with the same 79-byte body (`invalid_token`, "Missing or invalid access token") and a bearer challenge whose `resource_metadata` names `https://mcp.wix.com/.well-known/oauth-protected-resource/mcp`. That document (124 bytes) names `https://mcp.wix.com` itself as the only authorization server and one scope, `offline_access`. The issuer's metadata (519 bytes) has ten keys: authorize, token and register endpoints on the same host, `token_endpoint_auth_methods_supported` including `none`, grant types `authorization_code` and `refresh_token`, and `code_challenge_methods_supported` of `plain` and `S256`. No `client_id_metadata_document_supported` key. It is key-for-key the same shape as the document `mcp.atlassian.com` serves at its own root (`p-20261017-atlassian-resource-host-as-metadata-second-issuer`); the reporter's reading, not the vendor's statement, is that both come from one OAuth-provider library. Nothing was registered and no token was sought.

**A Wix site's MCP: yes, on the one site measured.** The vendor's documented example, `https://andream.wixsite.com/andreas-kitchen/_api/mcp`, answers 404 with a 14-byte body reading "Site not found" (06:12:27Z; the transcript types it text/html and withholds it in place, so the words are in its addendum), so the page's own example is gone. A live site found by web search, `celebrationsbakery.wixsite.com/celebrations-bakery`, answered `initialize` 200 at 06:12:29Z with `serverInfo.name` "Site Visitor Assistant for site \"Celebrations Bakery\"" and `protocolVersion` `2025-06-18`, and `tools/list` 200 with 39,058 bytes naming **ten** tools: `WixREADME`, `ReadFullDocsArticle`, `ReadFullDocsMethodSchema`, `BrowseWixRESTDocsMenu`, `CallWixSiteAPI`, `GenerateVisitorToken`, `SearchSiteApiDocs`, `GetBusinessDetails`, `SearchInSite`, `ExecuteWixAPI`. The vendor's page lists seven; `WixREADME`, `BrowseWixRESTDocsMenu` and `ExecuteWixAPI` are on the wire and not on the page. No tool was called; the two requests above are the ones the vendor's page itself shows.

Two of the undocumented tools deserve their words on the record. `ExecuteWixAPI`: "Run JavaScript against the Wix REST API on site \"Celebrations Bakery\" (...), on the visitor's behalf. The code runs in a sandbox and you get back whatever it returns." and "PREFER THIS TOOL OVER CallWixSiteAPI". `WixREADME`'s 5,282-byte description carries a block tagged agent-mandatory-instructions that opens "YOU MUST READ AND FOLLOW THE AGENT-MANDATORY-INSTRUCTIONS BELOW" and states "You are an agent that helps the user manage their Wix site." That sentence is served to an anonymous visitor's agent on a visitor-facing endpoint; what it does with a visitor token is not measured, and the registry records the text as the vendor's wire, not as a finding about effect. A tool description that instructs the reading agent is, for this registry, inbound content.

## Re-read five days on, with the controls the first pass did not run

Four records carry what follows, each one request's claim: `p-20261022-wix-mcp-keyless-401-any-method`, `p-20261022-wix-prm-path-specific-two-resource-identities`, `p-20261022-wix-site-mcp-keyless-ten-tools`, `p-20261022-wix-site-mcp-get-401-post-200`. The transcript is the 2026-10-22 reading linked above; nothing was registered, no token was sought and no tool was called on either server.

Every wire claim in the section above reproduces on 2026-10-22, two of them byte-identically: the owner-facing 401 is still 79 bytes with the same digest and the same `resource_metadata` pointer, and the site MCP's `tools/list` is still 39,058 bytes, now pinned by a sha256 and re-sent 31 seconds later for the same digest. Four things are new, and three of them are controls.

**The method decides the answer on the site MCP.** A plain GET of the same site URL that answers a keyless POST with 200 and ten tools answers **401 with 76 bytes**, `invalid_token`, "Missing Authorization header". The two 401s on this vendor are different documents: `mcp.wix.com` serves 79 bytes reading "Missing or invalid access token" with a discovery pointer, the site serves 76 with none. A survey probing MCP endpoints with GET would file this keyless surface as account-gated, and the registry's own link gate GETs the surfaces a record names, which is why both readings are filed under the one URL. On `mcp.wix.com`, by contrast, a GET answers **byte-identically to the two POSTs**: no 405, no JSON-RPC envelope, so there the method tells a reader nothing.

**The protected-resource document is path-specific here, and only a control shows it.** An invented path under `/.well-known/oauth-protected-resource/` answers 404 with 13 bytes, so a 200 from that prefix on this host is evidence that the path is a declared resource. `mcp.figma.com` serves its one document for any path including an invented one; `mcp.asana.com` 404s. The host also serves **two** documents: the path-inserted URL declares `resource` as the `/mcp` path, the well-known root declares the bare origin, both naming the host itself as the only authorization server.

**The agent-mandatory-instructions block is in four of the ten tool descriptions, not one.** `WixREADME`, `ReadFullDocsArticle`, `ReadFullDocsMethodSchema` and `BrowseWixRESTDocsMenu` each carry one, 22,052 characters between them, every one stating "You are an agent that helps the user manage their Wix site." on a visitor-facing endpoint. Counted as occurrences over the whole body; a line count of any of those phrases is 1 by construction, because the answer is a single line of JSON. The registry records the text as the vendor's wire and not as a finding about effect.

The vendor's own documented example site, `andream.wixsite.com/andreas-kitchen/_api/mcp`, is still 404 ("Site not found") five days on, and an invented path on the live site answers 403 with Wix's HTML refusal page, so the 200 belongs to the documented path rather than to the hostname.

## The claim (mkt.build-website): the vendor's words, and who owns the result

The [job](https://public-agents.com/jobs/mkt.build-website) asks for a site live at the business's own domain, usable on a phone, with "the domain, the hosting and the files in the business's own name". The vendor's claim, from `llms.txt`: "Wix AI Website Builder generates a full mobile-friendly site from a chat — pages, layout, text, images — and adds business solutions to refine in the editor." The [AI website builder page](https://www.wix.com/ai-website-builder) says "Launch your AI-built site with a custom domain name" and, on the FAQ, that hosting is included and "When you upgrade your site to any Wix Premium Plan, you’ll receive a voucher for a free domain of your choosing for one year"; the same page says that to connect custom domains "you'll need to choose a Premium Plan".

The ownership half is where the vendor's own pages bound the claim. [Exporting or Embedding Your Wix Site Elsewhere](https://support.wix.com/en/article/exporting-or-embedding-your-wix-site-elsewhere): "your site must run on Wix’s servers"; "the content you build on Wix belongs to you"; "The reason you can't use another host for your Wix site is that the SaaS architecture does not support external hosting"; and "To connect a domain to your Wix site, you must upgrade your site with a plan". A domain bought from Wix can be transferred to another registrar, per the vendor's transfer article (read in search results only, not archived; not quoted). So the business owns its content and its domain and does not own portable site files: the job's description says "a site the business cannot move is a different product from one it can", and this is the second kind. Whether the chat-built site is accepted without a rebuild, and how long brief-to-live takes, are the job's measures and nobody has published them. The Wix MCP's "creating and publishing a site" is an account-level action the owner's agent can take; that is the vendor's statement and was not exercised.

Wix Symphony is a separate claim this entry records and does not file as a job: "Wix Symphony is an AI agent platform that builds businesses a team of specialist AI agents — outreach, marketing, scheduling, research, finance, and design — that plug into existing tools and proactively run and grow the business from one conversation." Nothing on the page names a job this registry defines in terms that could be checked.
