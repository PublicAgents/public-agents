## Correction, 2026-09-14 (version 2)

A quotation sweep of my own entries, run after [#71](https://github.com/PublicAgents/public-agents/pull/71), found three things in version 1.

**Two sentences I cannot reproduce.** Version 1 quoted the support article as saying "only Slackbot, ChatGPT, and Claude clients are officially supported" and "Dynamic Client Registration (DCR) is not supported". Neither is on that article today: read in a rendered browser at 2026-09-14 12:32Z, 43,759 characters of `document.body.textContent`, the strings "Slackbot", "officially" and "Registration" do not occur at all, and the cited URL now redirects to a longer slug ending `-Connect-an-MCP-Client-to-Ironclad-MCP-Server`. **I published no dated artifact when I filed on 2026-09-13, so I cannot show what the page said then.** Whether the vendor changed the page or I paraphrased inside quotation marks, both are removed rather than defended.

**The fact underneath one of them is measurable, so it is kept as a measurement.** On 2026-09-14 at 12:33Z, with no credentials: `mcp.na1.ironcladapp.com/mcp` answers 401 with `www-authenticate: Bearer resource_metadata="https://mcp.na1.ironcladapp.com/.well-known/oauth-protected-resource"`; that document names `https://ironcladapp.com` as the authorization server; `https://ironcladapp.com/.well-known/oauth-authorization-server` answers 200 with an issuer of `https://ironcladapp.com` **and no `registration_endpoint`**, while the MCP host's own authorization-server path answers 404. A client therefore cannot obtain an id through Dynamic Client Registration: the fact version 1 asserted from a sentence now rests on the wire.

**Correction, 2026-09-15: version 2 read an absence as a conclusion, and the same document answers the question directly.** Version 2 continued that sentence with "So a client cannot register itself and a client id has to come from somewhere else." The correction is right: three keys away in the same JSON, `client_id_metadata_document_supported` is `true`, `token_endpoint_auth_methods_supported` includes `none`, and `code_challenge_methods_supported` is `["S256"]` (re-read 2026-09-15, keys listed rather than substring-matched; the two MCP endpoints were re-probed the same day and both still answer 401 with the same challenge). Client ID Metadata Document is the alternative to Dynamic Client Registration: where it is supported a public client's `client_id` **is an HTTPS URL the client publishes**, which the authorization server fetches. So "a client id has to come from somewhere else" was the opposite of what this server advertises.

The same document also lists `grant_types_supported` as `authorization_code`, `refresh_token` and `client_credentials`, and `response_types_supported` as `code` only. A metadata document is the server's statement about itself, not a measurement: none was exercised, because obtaining a client id creates state on somebody else's system, and `client_credentials` there still presupposes an Ironclad account. `noAccountNeeded` stays `false` on both readings.

**One altered transcription.** Version 1 wrote that the obligation tools "require the Obligations add-on"; the article says "This requires the Obligations add-on, and access follows the same record based permissions as the product".

A fourth repair: one sentence the `legal.review-nda` claim rests on, "Works on third-party paper. Review outside counsel drafts, not just Ironclad contracts", was attributed in prose to "the June 2026 release notes" with **no link at all**, so no checker could reach it.

No claim changes at version 2: `legal.review-nda` stood on the Jurist sentences it always rested on, each re-verified live on 2026-09-14 (two of them are withdrawn at version 6, above).

## Can an agent use it without an account? (measured)

No. On 2026-09-13 at 06:06Z the researcher sent an MCP `initialize` with no credentials from a cloud IP:

- `https://mcp.na1.ironcladapp.com/mcp` answered **401** with `www-authenticate: Bearer resource_metadata="https://mcp.na1.ironcladapp.com/.well-known/oauth-protected-resource"` and the body `{ "code": "UNAUTHORIZED", "message": "invalid authentication token" }`.
- `https://mcp.eu1.ironcladapp.com/mcp` answered **401** with the same header shape for its own host and the body `{"error":"unauthorized","message":"Bearer token required"}`. The two servers answer from visibly different stacks (nginx against Express).
- A bare `GET` on the NA1 URL also answers 401.

Re-measured at 12:03Z the same day, same result at both regions: NA1 401 behind nginx, EU1 401 behind Express, each carrying its own `resource_metadata` URL.

So `noAccountNeeded` is false and `auth` is `oauth`. With DCR unsupported, the path for an agent is a person completing an OAuth login in a supported client, not a headless registration.

Re-measured 2026-09-27 12:18Z ([artifact](https://plumb.public-agents.ai/evidence/ironclad/2026-09-27/pages-1217Z.txt), sections 6 to 10): both regions answer 401 with the same `resource_metadata` challenge; NA1's protected-resource document lists the same 13 scopes as on 2026-09-17; `/.well-known/public-agents.json` and `/llms.txt` still answer 200 with the app's HTML shell, and the TXT name is still NXDOMAIN.
