Norviq is an Apache-2.0 open-source project that governs what an AI agent's tools may do rather than what a model says. Its [repository README](https://github.com/norviq-dev/norviq/blob/main/README.md) calls it "Runtime policy enforcement for LLM agent tool calls on Kubernetes." and describes "a policy enforcement point (PEP) that sits between an AI agent's reasoning loop and the tools it can call". The GitHub API returns the Apache-2.0 SPDX id for the repository, created 2026-05-28, with v0.2.8 the latest release (2026-11-12) and the default branch last pushed 2026-11-14. The site footer reads "© 2026 Norviq · Apache 2.0"; there is no published hosted or paid edition.

## The surface an agent reaches

Before a tool runs, the call is sent to Norviq and answered "allow, block, escalate, or audit". Two integration paths send it, per the README: an injected Kubernetes sidecar that POSTs each tool call to the central API at `POST /api/v1/evaluate`, with "zero-code-change" for the agent; or an in-process SDK that wraps the tool-calling point of a framework so a block or escalate decision raises before the tool runs. The README names SDK adapters for LangChain, LangGraph, CrewAI, AutoGen and Semantic Kernel. A separate MCP action-firewall runs as a stdio proxy in front of an MCP server, so "every `tools/list` and `tools/call` goes through the gates on the way past".

The decision is OPA/Rego, scoped to identity. The README: a tool call is "evaluated against OPA/Rego policies scoped to the workload's Kubernetes/SPIFFE identity", and the engine returns the verdict plus the `rule_id` and a reason. By default a webhook mints a per-workload HS256 token at sidecar injection; SPIFFE/SPIRE SVIDs are opt-in. Because Norviq is self-hosted, there is no vendor-hosted endpoint to probe: the API and engine run wherever the operator deploys the Helm chart (`oci://ghcr.io/norviq-dev/charts/norviq`, cosign-signed, images digest-pinned). The first-hand evidence here is the public Apache-2.0 source and its documentation, not a live hosted call.

## Why it claims it.review-agent-tool-actions, and where the claim stops

The job asks that a high-risk agent tool action receive a policy decision before it can change systems, with allowed actions proceeding and others denied or sent for a human decision. That is what `/evaluate` returns. The README's Scope section states it plainly: "Norviq decides whether an agent's tool call may run, before it runs." An escalate verdict is the job's human-decision path; `audit` logs without blocking, for trialling a policy observably. The decision is per-call, on the call's inputs (`tool_name` and `tool_params`), and "OPA/Rego evaluated per tool call, sub-second."

Three limits keep the claim bounded, and each is the kind the job definition itself names.

First, the gate is cooperative, and the default posture is fail-open. The README is explicit that this is not network interposition: "Norviq authorizes the call, it does not sit in the tool's network path", and "This is cooperative: agent code that calls a tool without asking reaches it unjudged". The opt-in `agentEgressPolicy` bounds that bypass at the network layer, but it is off unless configured, and the security model is candid about how narrow it is even when on: it "does not restore per-call parameter policy", it "requires a NetworkPolicy-enforcing CNI (Calico/Cilium; kindnet silently ignores NetworkPolicy)", and within its scope "an agent may still freely reach anything on the allowlist without a verdict" — the threat table grades a full SDK bypass only "Partially" closed. Fail-open is also the shipped default on failure: the README notes "an unreachable engine and a namespace with no policy proceed by default" (allow), and the [security model](https://github.com/norviq-dev/norviq/blob/main/docs/security-model.md) adds that "no_policy_decision ships as allow". Both can be set to block/deny, but the out-of-box posture lets a call through when the engine is unreachable or no policy is loaded. This is the job's own caveat, "a review record alone is not proof that an action was blocked", made concrete: coverage depends on the integration routing every risky call through `/evaluate` and on the operator having written or enabled an enforcing policy.

Second, there is nonetheless a real enforcement floor, and it is where Norviq sits apart. The security model states "The shipped namespace baseline enforces, from 0.2.6.": every namespace listed at install gets a `strict` baseline whose 21 controls act, "20 act on a matching call (17 refuse it", one records. And within a namespace the operator has chosen to enforce, "evaluation is fail-closed": per the security model, "if OPA errors, times out, or the caller's SPIFFE identity is malformed, the call is blocked rather than silently allowed." So a call a baseline control refuses does not reach the tool through the cooperative path, and an evaluation failure inside an enforcing namespace denies rather than allows. The README's local MCP mode, by contrast, is honest that it enforces nothing: "Local mode is a scanner and a change detector, not an enforcement point." The guiding principle the security model states for why the floor is narrow: "a block is something a customer asked for".

Third, the policy is operator-authored. The governing rules are OPA/Rego the operator writes, layered by priority with tighten-only overlays, scoped to a workload's Kubernetes/SPIFFE identity. That is where Norviq sits relative to a model-scored guard: the operator authors the policy and the identity binding, and the verdict is a Rego evaluation, not a model's score of the call. The README describes a "Red-team suite" of "built-in adversarial tests (prompt injection, encoding/nesting evasion, SQLi, PII/PCI exfil) that prove a policy actually blocks" — the project's own test harness, a claim to record as a claim, not a third-party measurement.

## Where it sits among the three claims on this job

The registry now lists three tools against `it.review-agent-tool-actions`, and they divide by who authors the decision and how close it gets to enforcement. MCP Guard is a hosted judge whose advisory verdict combines a vendor-set DeBERTa classifier's score with three vendor-fixed deterministic rules; the agent honours the result. Tool Guard Core is a self-hosted engine evaluating operator-authored YAML (which may itself invoke a model classifier); it decides and records, and the caller enforces. Norviq is the third pole: operator-authored OPA/Rego scoped to Kubernetes/SPIFFE workload identity, with a shipped baseline that refuses calls out of the box and a fail-closed path inside an enforcing namespace. By architecture, not by any measured comparison — none was run here — it reaches nearest to preventing the call: the enforcing baseline refuses matching calls at the decision layer, and the opt-in `agentEgressPolicy` can bound bypass at the network layer, though only on a NetworkPolicy-enforcing CNI and only up to an allowlist an agent may still reach without a verdict. It is still, at the decision layer, cooperative, and fail-open by default. None of the three sits in the tool's network path as the whole of its defence.

## Access and ownership

Reaching the decision needs no vendor account: an operator installs the Helm chart and the agent-facing call is `POST /api/v1/evaluate`, carrying an operator-minted per-workload token, so `noAccountNeeded` is true and `auth` is none at the vendor boundary (how the operator protects their own deployment is their choice). No `/.well-known/public-agents.json` was served at the homepage (404 on 2026-11-21), so provenance is third-party and this entry is unverified, in those words, until the domain acknowledges it.

## Pricing

Norviq is free: Apache-2.0 open source, and self-hosted. There is no billing. The site publishes no hosted or paid edition and no pricing page (404 on 2026-11-21); the footer reads only "© 2026 Norviq · Apache 2.0". It is not machine-payable: there is no agent-settled payment path.

## Measures

All of the job's measures are empty. No third-party figure for the share of high-risk actions checked before execution, unauthorized actions executed, false-positive reviews, or time to a human decision was found. The security model reports that the shipped baseline "was switched on with evidence" of zero false positives over a 51-case benign corpus in the project's own red-team precision test; that is a first-party test result, not a third-party measurement, and it covers the benign corpus, not production traffic. The README's "sub-second" is the project's own latency statement, and the job's latency measure asks a different thing: how quickly actions needing human approval are resolved, a workflow time rather than the engine's evaluation time.
