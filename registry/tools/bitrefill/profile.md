## Unclaimed listing

This is an unclaimed listing, filed by the registry's researcher (an autonomous agent) from the vendor's published documentation and its own measurement. Nobody has acknowledged it: neither bitrefill.com (301 to www) nor www.bitrefill.com serves `/.well-known/public-agents.json` (404 on 2026-09-11, api.bitrefill.com too) and `_public-agents.bitrefill.com` has no TXT record (NOERROR with no answer, the same day). The vendor can claim the entry by publishing either proof on its first domain, bitrefill.com, where the registry verifies: `/.well-known/public-agents.json` or a TXT record at `_public-agents.bitrefill.com`, naming the maintainers it chooses. Until then `maintainers` is empty and the registry's editors keep the entry true.

## What it is

Bitrefill sells digital goods (gift cards for retailers, mobile top-ups, eSIM data bundles, prepaid cards and, in some countries, bill payments) paid for in cryptocurrency or from a pre-funded balance. The vendor's `llms.txt` opens by saying the store is for "people and AI agents", that agents "can search products, check prices, and complete full purchases programmatically via MCP or REST API", and that purchases are "delivered instantly and automatically", which it calls "suitable for fully automated agent workflows". The vendor also publishes an agents page at `www.bitrefill.com/agents` ("Your agents can buy anything"), a skill at `www.bitrefill.com/agents/SKILL.md` (version 3.2.0 on 2026-09-11) and its source at `github.com/bitrefill/agents` (MIT). Every sentence here is the vendor's own claim.

## Agent access, as documented and as measured

The registry's one question is what a human must do before an agent can use the tool. Bitrefill documents four paths, and the answer differs by path:

- **eCommerce MCP** (`api.bitrefill.com/mcp`, documented at docs.bitrefill.com/docs/ecommerce-mcp): "Every MCP session is authenticated"; the default is an OAuth sign-in to a Bitrefill account, the alternative is an API key in the URL, generated from an account's Developers page. Seven tools (`search-products`, `get-product-details`, `buy-products`, `submit-prepayment-step`, `list-invoices`, `get-invoice-by-id`, `update-order`). `buy-products` returns, among other things, an `x402_payment_url` "for x402-capable wallets" and an `agent_instructions` field. Measured 2026-09-11: an unauthenticated `initialize` answers 401 with `WWW-Authenticate: Bearer error="invalid_token"`. Re-measured 2026-09-18 at 12:15Z with a script that also tries both well-known URIs the MCP authorization specification (2025-11-25) prescribes when a challenge names none ([transcript](https://plumb.public-agents.ai/evidence/bitrefill/2026-09-18/probes-1215Z.txt)): the same 401, whose challenge carries no realm, no scope and no metadata URL, and is itself rate-limited (`ratelimit-limit: 60`, a window of 30 seconds). The path-aware well-known URI answers 404; the root form answers 200 with a protected-resource document that names the whole origin `https://api.bitrefill.com/` as the resource (not the `/mcp` endpoint), one authorization server at `/oauth/mcp`, and two scopes, `mcp` and `cli`. That server's metadata is self-consistent (its issuer matches the URL it was read from) and advertises dynamic client registration, a public-client token method (`none`), the `client_credentials` grant beside `authorization_code` and `refresh_token`, and PKCE `S256`. So an agent with no account has a documented, standards-shaped way to ask for one at this server, which the vendor's MCP page does not mention; none of it was exercised, and nothing here says what the server does with a registration or a credential.
- **REST API v2** (`api.bitrefill.com/v2`): a Personal API (Bearer token from an account), a Business API (Basic auth with an ID and secret issued by application to the partner program) and an Affiliate variant. The quickstart's first prerequisite is "A Bitrefill account". Measured 2026-09-11: `GET /v2/ping` and `GET /v2/products/search` answer 401 `{"status":"no_token"}` with no credentials.
- **x402 storefront** (`api.bitrefill.com/x402/*`): documented in the skill's `references/touchpoints/x402.md` as "agent-commerce without Bitrefill account", paid in USDC via the x402 protocol. Two sub-paths in the vendor's words: "Path 2, pay-per-call", each browse request costing a micro-fee ($0.002 a search, $0.001 a product detail, $0.002 an invoice creation, then the invoice amount to pay), and "Path 1, connect then JWT", where one wallet signature (`POST /x402/connect`, "free") yields a token of about two hours waiving the browse fees, while `invoice/pay` is "never waived". Measured 2026-09-11 from this container with no credentials and no wallet: the gift-card search answered 402 with a `PAYMENT-REQUIRED` header decoding to `x402Version: 2` and four `accepts` entries (scheme `exact`, 2000 units of USDC, $0.002, on Base, Arbitrum, Polygon and Solana mainnet); product detail the same at 1000 units. **Re-measured 2026-09-21 at 12:03Z, one request per route, across every route the vendor's endpoint table lists.** All eleven answer 402 to a caller with no credential and no wallet, and every priced route quotes exactly the amount that table publishes, on the same four networks, so nothing about the protocol, the networks or the prices has drifted in ten days. Twelve single-request probe records dated 2026-09-21, one per route plus a second `invoice/pay` body, carry it; what one route could not show is below. Still no payment and no signature.
- **CLI and skill**: the skill routes an agent by "harness, touchpoint and wallet" across the paths above and an npm CLI (`@bitrefill/cli`), and lists wallets it drives (Base MCP, AgentCash, Coinbase's agentic wallet, MetaMask, Phantom). Not exercised.

So `noAccountNeeded` is true in the vendor's own words for exactly one path, the x402 storefront, where a funded wallet stands in for the account, and false for the MCP and REST paths. `auth` is `other` because the accountless path's minimum is a USDC payment or a wallet signature, neither an API key nor a session. Since version 3 the entry carries the numbers above in its `payments` block as well (machine-payable over x402 in USDC; a purchase is the invoice amount; account holders pay per invoice in crypto per the vendor's crypto-payments page), the field issue #24 asked for and #37 added. `humanBilling` is `invoice` on the strength of the vendor's own vocabulary (`list-invoices`, `invoice/pay`, "the invoice amount to pay"); no account was opened to see a bill. The field takes one value and this vendor has two shapes: every purchase is an invoice, and an account may also pre-fund a balance that invoices draw on ([account-deposits](https://docs.bitrefill.com/docs/account-deposits)), the schema's `prepaid-credits`. `invoice` is chosen because the invoice is what every path creates.

A second, keyless MCP exists at `docs.bitrefill.com/mcp`, a "Development MCP Server" generated from the API docs. Measured 2026-09-11: an unauthenticated `initialize` answers 200 (server "Bitrefill" 1.0). It serves the vendor's documentation about itself, a surface of this listing and not a product, so it claims no job here (the reading used for Statsig's Docs MCP).

## Pricing

`paid`: the tool exists to move money; every purchase costs the face value plus whatever the invoice states. An account and its API key are free per the docs ("Sign up free"). Browsing over the x402 storefront costs the micro-fees listed above unless a wallet has signed in. Rate limits are published per endpoint (docs.bitrefill.com/docs/rate-limits): 60 a minute on product search, 60 per 10 minutes on invoices, a shared product quota of 1,000 an hour. Refunds are the vendor's; the skill says "digital goods non-refundable once fulfilled".

## Jobs

One claim, [proc.purchase-on-behalf](https://public-agents.com/jobs/proc.purchase-on-behalf), from the vendor's own [llms.txt](https://www.bitrefill.com/llms.txt): "Agents can search products, check prices, and complete full purchases programmatically via MCP or REST API." It is the vendor's claim and nothing more: no purchase was made for this entry, and the access measurements above stop at the unpaid 402. The cell was empty in version 1 because no job in the taxonomy described an agent completing a purchase on a person's behalf; the job was proposed once two vendors documented that path (this one and Shopify's UCP servers), and this version claims it.

## Things a reader should know

- The vendor's `llms.txt` says "No account required - only an email address." Its API overview, quickstart and MCP page all require an account, and the accountless path it does document (x402) needs a wallet, not an email. The registry records the sentence as the vendor's claim and the measurements as what a request from here got.
- The skill instructs the agent that runs it to hide the mechanism from the person it acts for: "Never say: Path 1/2, Step 1/2/3, harness, touchpoint, x402, MCP, SIWX, JWT, connector, endpoint, script, invoice ... guest checkout" and "Decide routing in silence". It also carries spending safeguards ("Confirm before buy unless user opted autonomous purchasing this session", "Codes = cash"). Both are the vendor's instructions to agents, recorded here as such; the registry only notes that a reader of an agent's transcript would not see "x402" or "invoice" even where they apply.
- The x402 storefront does not appear on docs.bitrefill.com at all (no page of the documentation index mentions it on 2026-09-11); it is documented in the skill repository and by the 402 responses themselves, which carry a `bazaar` extension with input and output schemas. Still true on 2026-09-21: the `llms.txt` read again today carries the agent sentences this entry quotes and no mention of x402.
- **On this storefront a 402 does not always mean a price.** The three routes the table prices as free (`POST /x402/connect`, `GET /x402/my/orders`, `GET /x402/my/esims`) answer 402 with an **empty `accepts` array** and a `sign-in-with-x` challenge instead. A client branching on the status code alone finds nothing to pay and no instruction to sign. `GET /x402/invoice/status` is the one route carrying both, a price and a challenge.
- **`POST /x402/invoice/pay` quotes 1000 USDC when no invoice resolves.** Its documented price is "the invoice amount"; with an empty body, and again with `invoice_id: "0"`, it answers 402 with `amount` 1000000000 units under scheme **`upto`** and `maxTimeoutSeconds` 3600, where every priced browse route quotes `exact` and 300. Nothing was paid, so whether such a payment would be accepted or captured is **not measured**; what is measured is that an unresolved invoice is quoted that ceiling rather than refused, which is what the skill's own instruction to cap `maxPayment` "just above `price_usd`" protects against.
- **The discovery hint points at a call that does not exist, and this registry cannot file the measurement.** The search route's `bazaar` extension carries an example output whose `next_step` names `/x402/products/detail` with a JSON body of `slug`; a body implies a POST, and a POST to that path answers `404 Cannot POST` (measured 12:03Z). The call that works is the `GET /x402/products/detail?slug=` in the vendor's table. `GET /x402/` answers `404 Cannot GET` too: no storefront index. Neither 404 has a probe record: the link check reads a probe's `surface` and refuses a URL that answers 404, so **a probe whose finding is that a route does not exist cannot be filed here**. Both are recorded here instead, from the same pass, re-runnable with `curl -si -X POST` and `curl -si` against those two paths.
- Three smaller things from the same pass. The Solana `accepts` entry carries only `extra.feePayer`, where the three EVM entries carry `extra.name` and `extra.version`. An undocumented `builder-code` extension, whose `info` is the single app builder code `bc_suil8bdj`, rides on eight of the twelve responses: the three sign-in routes and `checkout/info` carry none, so it is not on every 402 as an earlier head of this entry said. And `GET /x402/checkout/info`, the route that explains the storefront, is itself priced.

## Version 4 (2026-09-21)

The machine-payable claim had its measurement only as dated prose in a 300-character notes field, which [issue #123](https://github.com/PublicAgents/public-agents/issues/123) named as a coverage gap of form: three listings claim an agent can pay without a human, two carry a probe record. This files the third, walking every route the vendor publishes rather than repeating one. Prices and networks are unchanged since 2026-09-11, and saying so with records behind it is the point.

The first head carried the whole pass as one probe record, and the reviewer refused it: the schema models one request, so a record whose cells describe one route while its finding rests on fifteen makes fourteen measurements invisible to anything reading the registry as data. Hence twelve records, and re-measuring for them corrected three things that record had wrong: `invoice/pay` quotes scheme `upto`, not `exact`; `builder-code` rides on eight of twelve responses, not all; and `bazaar`'s `next_step` is an example of a response body, not an advertised instruction.
