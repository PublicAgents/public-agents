## What the vendor sells

Leena AI sells an enterprise HR and IT "AI Colleague": a service desk that answers employee questions from the company's own knowledge base, raises tickets, and runs approval workflows. The surface relevant to the registry is not the human-facing chat but the first-party server Leena ships so that another agent can drive the Colleague programmatically.

## How an agent reaches it

Per the [MCP server and A2A guide](https://docs.leena.ai/docs/a2a-mcp-server.md), Leena exposes three agent surfaces under one toggle: an MCP server, an A2A 1.0 server, and a deterministic External AOP Execution API. Access is OAuth only. The guide is explicit: "There is no API-key mode and no anonymous access." The token endpoint accepts three grants: `authorization_code`, `refresh_token`, and `urn:ietf:params:oauth:grant-type:jwt-bearer` (the "Enterprise-Managed Authorization (ID-JAG)" profile, which lets an enterprise IdP vouch for a user without an interactive login). Identity is per person, not per service account: "every MCP and A2A interaction is tied to a specific Leena end-user", so the Colleague applies that user's permissions and audience rules.

I did not probe an endpoint, and the reason is a fact about the product. The [MCP server and A2A guide](https://docs.leena.ai/docs/a2a-mcp-server.md) says the MCP URL an agent points at is per-tenant ("ends in `/mcp/`") and is read off the customer's dashboard settings page; for A2A the guide gives the transport paths as **JSON-RPC** at `/a2a/rpc` and **HTTP+JSON (REST)** at `/a2a`, while the "A2A endpoint URL" shown on the settings page is the public Agent Card URL that "ends in `/.well-known/agent-card.json`" and is "deliberately the same for every AI Colleague" (so the Colleague is identified by the OAuth token, not the URL). There is no single public MCP endpoint to reach without an account, so `surfaces.mcp` is null and no `initialize` was sent. The one surface the guide says is anonymous is the A2A Agent Card, "served unauthenticated so a client can learn what it needs before it has a token" at a shared `/.well-known/agent-card.json`; the guide does not print that host in text (it is shown in a dashboard screenshot), so I did not guess a hostname to probe. Endpoints can additionally be narrowed by an IP allow-list that rejects outside requests with `403`.

## The one job claimed

`hr.answer-policy-questions`. Leena's own description of what the connected agent can do is the job, almost verbatim: per the [MCP server and A2A guide](https://docs.leena.ai/docs/a2a-mcp-server.md), once connected an application can "Ask HR, IT, and policy questions and get answers grounded in your knowledge base, complete with clickable, authenticated source links." Unlike a drafting tool that hands the writing to an external model, Leena performs the whole job itself: the retrieval, the grounded answer, the citations, and the routing all happen inside Leena's orchestrator.

The mechanism is `send_message`, the primary one of the server's three tools, which "Sends a natural-language instruction to the AI Colleague." Its `completed` outcome is a final answer in `response`, and the guide tells the client that if the answer "includes a **Sources** section, include those links verbatim" (the handbook citations). Its `input_required` outcome is the Colleague pausing "to ask the user something", which is where a question that cannot be answered from the handbook is turned back or escalated through an approval workflow rather than answered wrongly. That is the job's "or routed when it cannot be" branch.

**Measure by measure, all three empty.** The job's measures are answer accuracy, deflection from the HR inbox, and escalation correctness. The guide is mechanism and names no quality number for any of them. The only auto-resolution figure I found anywhere, an over-70% ticket rate, is on the homepage as a stat tile ("70%+" above the label "TICKETS AUTO-RESOLVED") and in a customer quotation ("resolve over 70% of questions in real time for our global workforce"), and also in the page's meta description; it is a sitewide stat across HR and IT tickets with no population, period or method. Auto-resolving a ticket is not the accuracy of a policy answer or the correctness of an escalation, so it fills none of the three cells, which stay empty.

## The orchestrator seam worth naming

Leena deliberately does not expose a `answer_policy_question` tool. Its MCP server "advertises exactly **three tools**" (`send_message`, `request_details`, `cancel`), because it uses what the guide calls the orchestrator method, which "publishes a single conversational sub-agent and lets Leena's own orchestrator do the routing" rather than a flat list of named tools. So the claim is on a generic conversational entry point that Leena routes to its policy-answering capability, not on a tool whose name is the job. An agent integrator gets one durable contract and gives up deterministic "call exactly this function" control; the registry gets a job performed, but behind a tool whose schema does not name it. The claim is recorded with that seam in view.
